# v0.3 — Local AI Engine

## Scope and current implementation

This branch introduces the model-independent application boundary before native runtime integration:

- `AIEngine`: suspendable local text-generation contract; model-specific code stays behind this interface.
- `LocalTaskAnalyzer`: AI-first task analysis with the existing `TaskAnalyzer` as deterministic fallback.
- Strict output parsing: only the four existing `TaskType` values are accepted; malformed or unknown output falls back to rules.
- Bounded input/output sizes and a human-review flag for engagement/account-impacting workflows.
- Coroutine cancellation is propagated instead of being swallowed by fallback handling.

## Native runtime implementation in this branch

- Android NDK `27.2.12479018` + CMake `3.22.1`; package target is `arm64-v8a`.
- llama.cpp is fetched at immutable commit `b1b770d90d94cad9e9ea5b993bdbc383a522fb28` (release tag `v1.0.0`).
- `LlamaCppEngine` implements `AIEngine`, serializes native lifecycle operations, and runs load/inference on `Dispatchers.IO`.
- JNI loads GGUF, creates a CPU context, tokenizes prompts, evaluates and greedily samples up to 256 tokens, then frees model/context safely.
- Initial limits: 2048 context tokens, 2–4 CPU threads, prompt <= 16,000 characters, no GPU offload. Context and thread settings are bounded.
- Unit tests cover missing model, lifecycle, generation limit and invalid configuration using a fake native boundary.

The Qwen3 GGUF file is **not included** and the engine is not yet connected to the app's task-creation UI. The user must not commit model weights or package them in the APK. Next steps:

1. Add a user-controlled model import flow into app-private storage, with file size/hash validation.
2. Validate a specific Qwen3-1.7B Q4_K_M GGUF artifact and its license before exposing it as a selectable model.
3. Connect `LlamaCppEngine` to `LocalTaskAnalyzer` and show AI vs rule-fallback status in the UI.
4. Benchmark cold load, warm inference latency, tokens/sec, peak RSS/PSS, and thermal behavior on the Redmi K40 Gaming. Adjust context and thread defaults from measured results.

## Device profile and safety constraints

Target ABI is `arm64-v8a`. Start with CPU inference and a small context window (2048–4096) rather than assuming Mali GPU acceleration. Use bounded prompts and outputs. If memory pressure, model-load failure, or native errors occur, return to the existing rule analyzer. AI output is advisory: it cannot autonomously submit account actions or perform artificial engagement.

## Acceptance criteria

- Existing v0.2 unit tests continue passing.
- AI output maps only to known task types and bounded workflow steps.
- Empty, malformed, unavailable, or failed model output uses the legacy analyzer.
- Coroutine cancellation is not converted into a fallback result.
- NDK/CMake builds the JNI library for `arm64-v8a` in CI.
- Native model loading and inference are verified on a physical arm64 device before enabling AI by default.
- Model weights remain external to the APK and repository.
- Device benchmark results are recorded before increasing context size or enabling parallel inference.
